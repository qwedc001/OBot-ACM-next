# 并发设计与实验

## 运行边界

`OBOT_JOB_WORKERS` 是后台队列同时执行的任务数，默认 4，可配置为 8；`OBOT_JOB_CAPACITY` 是等待队列容量，默认 32。它们不是 QQ 消息接收数，也不是整个机器人的 HTTP 请求数。队列满时拒绝新增任务；图片帮助遇到忙碌或渲染超时，退回同一权限过滤结果的文字帮助。

自绘图每个任务启动一个干净的 Python 子进程。独立解释器、字体缓存、原生图像对象和临时目录隔离并发状态；PNG 返回父进程后，由 ArtifactClient 按请求者保存。进程不是常驻池：代价是每次启动、导入、加载字体，收益是简单的故障隔离和明确的取消边界，不需要改写原版 renderer。

子进程不初始化 NoneBot，不读部署环境文件，不继承机器人凭据。backend 必须是可导入、可序列化的模块级对象；模型可以带预先下载的头像字节。内部 pickle 只在父进程创建的私有目录中交换，绝不作为公开上传格式。

超时、调用者取消或 RenderClient 关闭时先终止并回收进程，随后清理临时文件、释放队列位置。POSIX 使用独立进程组；Windows 处理虚拟环境启动器及其解释器子进程。文件准备／读取被取消时等待当前文件操作结束，避免临时目录清理竞态。失败只向调用者传递已知错误类型，不携带私有模型或原生报错正文。

Peeper 继续使用官方 CLI，每个请求复制到独立工作目录，移除全局 `render:peeper` 串行 key；不修改第三方源码、不改 CLI 参数语义。

## 异步链路检查

| 阶段 | 当前行为 | 保留的限制 |
| --- | --- | --- |
| QQ 接收／命令处理 | 当前 Adapter 独立分发事件；原生 matcher 和异步 Service 可交错执行 | 简单 `/ping` 不进入绘图队列；同一 handler 中显式 await 的多次发送保持顺序 |
| HTTP | 共用 httpx 异步连接池，总连接上限 32；JSON／HTML 解析转到线程 | 默认每个 origin 同时 4 个请求；CF API 保留 2.1 秒请求间隔及串行门闩 |
| 查询缓存 | 同查询合并在途请求；比赛来源并发聚合 | 避免重复请求，不把一次合并视作吞吐不足 |
| 数据库／文件 | ORM 异步会话；业务文件操作、摘要、解析转到线程 | SQLite 写事务及 Curation 的读改写锁保留一致性；不跨整个绘图流程持锁 |
| 榜单采集 | Hydro 请求异步；不同配置可以并行 | 同配置快照锁、Hydro 请求预算 4 保留 |
| 自绘图／Peeper | 每任务独立进程／CLI 目录，共享后台并发预算 | 默认 4，可选 8；图片大小和队列容量仍受限 |
| OCR | 独立后台任务，模型在线程内运行 | 共享 EasyOCR 模型仍使用 `ocr` key 和原生锁；取消等待不能强杀该线程 |
| 图片保存／QQ 发送 | 图片文件 I/O 转到线程；回复 client 无全局串行锁，await Adapter API | QQ 平台配额、上传网络延迟仍存在；Adapter 内的同步 Base64 编码是潜在事件循环开销，尚未实测成为瓶颈，不据此改写 SDK |

因此支持 4／8 个后台任务并行，不等于所有上游 API 都允许 8 并发。尤其 OCR 会占用共享队列位置；平台速率与事务一致性限制不能靠移除锁解决。

## 八线程与八进程实验

2026-10-18，本机 Windows、i9-13900HX（24 核／32 逻辑处理器）、32 GiB RAM，当前锁定 Python／Pixie 依赖。没有使用机器人账号、网络、生产数据库或真实用户资料。每批 8 个任务，每个方案重复 3 次，交替执行顺序，每批启动新的解释器。耗时为整批完成时间，包含排队、进程启动、绘制、PNG 传递，但不含网络、ORM 和 QQ 发送。

两种负载：

- 混合：帮助、比赛列表、比赛详情、资料卡各 2 张。尺寸分别为 4496×4655、3388×3696、1472×1049、1472×2043。
- 大帮助图：8 张 29 指令帮助图，每张 4496×4655。

线程组使用 8-worker ThreadPoolExecutor，调用同一套 renderer，不更改布局、字体或数据。另设“八线程＋绘图锁”对照，复现原有的串行绘图保护。进程组使用正式 RenderClient，每任务一个进程。

**无锁八线程的 6 个批次全部失败，不能给出有效耗时和内存收益。** 观察到 `pixie_font_layout_bounds`、`pixie_image_fill_text` 的内存访问异常，以及字体加载／对象释放异常。当前 easy-pixie 有共享 Typeface 缓存，原版 renderer 也有共享原生图像缓存；这些是需要调查的共享状态，但实验没有定位到唯一根因。结论只限于当前 Windows 依赖与实现，不宣称所有 Pixie 版本或 Linux 环境都不可多线程。

以下是成功方案的三次中位数；外部独立采样器统计整棵进程树，避免 GIL 阻塞采样。USS 为私有驻留内存，RSS 会重复计算跨进程共享页面，均按 MiB 计。

| 负载 | 方案 | 整批耗时 | 峰值 USS | 峰值 RSS | 每批最大事件循环延迟的中位数 |
| --- | --- | ---: | ---: | ---: | ---: |
| 混合 8 张 | 八线程＋绘图锁 | 8.08 s | 420 MiB | 443 MiB | 48.7 ms |
| 混合 8 张 | 八进程 | 3.93 s | 1349 MiB | 1485 MiB | 15.3 ms |
| 大帮助图 8 张 | 八线程＋绘图锁 | 14.36 s | 426 MiB | 449 MiB | 49.6 ms |
| 大帮助图 8 张 | 八进程 | 4.46 s | 3312 MiB | 3561 MiB | 15.6 ms |

加锁线程组比八进程分别慢约 2.1／3.2 倍，私有内存减少约 69%／87%，但实际同时绘图数是 1，不能称作八任务并行绘图。混合耗时范围为线程 7.73–9.21 s、进程 3.64–4.48 s；大帮助图为线程 12.80–25.64 s、进程 4.25–4.55 s。本机同时承担日常工作，存在明显尾部波动，三次结果不是严格的统计显著性检验或生产容量承诺。

另一次 1／4／8 进程混合负载单批对比为 16.10／4.72／3.56 s；这组 1 进程每张图都会重新加载字体，不能冒充原有常驻线程的串行基线。4 进程大帮助图单批为 6.74 s、绘图子进程合计峰值 RSS 1752 MiB，8 进程则约 3504 MiB。图片面积和中间画布才是主要内存来源，仅共享解释器无法让八张大图的画布消失。

选择默认 4 个后台任务；8 并发需按最坏图片尺寸和其他服务占用留足内存，不能仅以小资料卡测试决定。已有部署配置会覆盖新默认值。此实验没有改变生产配置，也没有测量 Linux 服务器端到端回复速度。

## 复现与测试

从 `backend` 目录使用项目虚拟环境 Python 执行：

```sh
python -m tests.benchmark_render_comparison --repeats 3
python -m tests.benchmark_render_comparison --repeats 3 --modes thread-locked process
python -m tests.benchmark_rendering --workers 1 4 8
python -m tests.benchmark_rendering --workers 4 8 --all-help
```

无锁线程实验在独立解释器中运行，失败不应发生在真实机器人进程内。基准只验证 PNG 头和尺寸，不替代视觉检查、线程安全证明或稳定性压测。

自动测试验证 4／8 个真实 PID 同时存活且 `/ping` 仍可响应，任务取消／超时／关闭后的进程回收、启动期间取消、失败后队列恢复、环境隔离，以及并行 Peeper 的目录／产物所有者隔离。没有用固定耗时阈值来断言渲染吞吐性能。
